# 供应商端 UI 设计思考：可读性、密度与列表操作

日期：2026-09-28

范围：本轮 20 条批注，以及全站文字层级、筛选栏、列表操作和分页。沿用已确认的浅色 V2 语言、Vue 3 / Element Plus 和现有业务流程。

## 1. 先让用户读懂，再让页面紧凑

供应商通常带着具体任务进入后台：找某笔订单、判断当前状态、处理退款或维护服务。因此页面应按“对象 → 状态 → 关键数值 → 当前动作 → 补充信息”的顺序组织。

此前的主要问题是辅助信息、已选值和占位提示颜色接近，字号集中在 10–12px，标题与数据差异不足。单纯把所有文字加深或加粗，会再次让整页等权。此次采用以下层级：

| 内容 | 字号 / 字重 | 颜色与用途 |
| --- | --- | --- |
| 页面标题 | 25–27px / 700–750 | `#20304A`，首先定位当前对象 |
| 区块标题 | 16px / 700 | 深色，明确阅读分组 |
| 行标题、订单编号 | 12–16px / 650–700 | 深色或链接蓝，便于扫描定位 |
| 正文、已选择的表单值 | 13–14px / 400–500 | `#34455C`，承担主要阅读 |
| 标签、日期、补充说明 | 通常 12px / 400 | `#53647A` / `#596A80`，可读但不抢主信息 |
| 未选择提示 | 13px / 400 | `#8590A1`，与已选值明确区分 |
| 金额 | 继承所在层级 / 700 | 保留状态语义色、等宽数字；两位小数，不加千分符 |

金额只强调数字；“累计支付”“待付”等标签仍然较轻。既处理 `money()` 输出，也处理旧退款历史里已经保存的金额文本。数据本身与资金计算规则不变。

## 2. 操作统一的是使用规则

一行中所有按钮都做成实心主按钮，会让多个动作同时争夺注意力；全部做成无差别链接，也无法快速识别待办。

| 场景 | 形式 | 示例 |
| --- | --- | --- |
| 页面级创建、弹窗确认 | 实心主按钮 | 发布服务、创建案例、保存资料 |
| 行内当前任务 | 浅蓝底 + 蓝色文字，28px 高 | 继续发布、上架、处理退款、上传合同 |
| 常规查看与维护 | 无底色文字按钮，悬停才显底色 | 详情、编辑、下架 |
| 风险操作 | 红色文字，沿用二次确认 | 删除 |
| 不可用动作 | 组件禁用态；资格解释由现有业务反馈承担 | 钱包未开通时的受限入口 |

服务卡片与订单列表使用同一套高度、字重、内边距和悬停反馈。服务操作按既有业务顺序排列；订单把当前任务放在详情之前。退款状态可以是红色提示，处理入口的颜色由动作层级决定。

## 3. 紧凑筛选，不挤压编辑表单

筛选控件统一为 32px 高，横向间距约 8–10px，页签上下内边距 8px。订单日期标签、“至”、输入框在同一中心线上。保留查询和重置的稳定位置，筛选值使用正文颜色。

编辑表单继续使用较舒适的 40px 控件，因为填写、纠错和上传需要更大操作空间。员工规模限制到 320px；长描述继续占满表单列。最多三项的擅长领域全部显示，地域这种可能很多项的选择仍保留按空间折叠。

内容宽度按信息性质区分：

- 多列业务列表最大 1440px，保留横向比较效率。
- 店铺资料、服务编辑器最大 1120px，编辑器的标题、内容和底部操作保持对齐。
- 1200px 为现有桌面布局下限，更窄时仍只在主内容区横向滚动。

## 4. 分页方案：明确页码，跟随列表底部

**本产品推荐使用分页，不使用无限滚动；分页栏处于列表末尾的正常文档流，不常驻悬浮。**

判断依据：

1. 订单、退款、服务和成员都是明确的管理对象，用户需要知道结果数量、当前范围，并能够跳页处理。
2. 无限滚动更适合连续浏览内容，会让管理列表长度和返回位置难以预测，页底也难以到达。
3. 全局吸底分页会持续占用可视高度，并容易与入驻/编辑的底部操作栏、验收入口形成叠层。当前数据密度可通过有限页长控制，优先节省屏效。
4. 筛选区继续按已有列表模式吸顶。翻页后自动返回列表顶部，避免新一页加载后仍停留在页底。

| 列表 | 每页条数 | 原因 |
| --- | --- | --- |
| 订单、售后、开票记录、成员 | 20 | 标准表格，支持批量扫描 |
| 服务、案例 | 8 | 每项包含图片、园区和规格，单条更高 |
| 已加入 / 可申请园区 | 各 9 | 匹配三列卡片，两个分组独立翻页 |
| 评价 | 10 | 包含评价正文和回复，沿用现有页长 |
| 开票订单选择 | 20 | 选中状态及合计跨页保留 |

全部复用 `ListPagination.vue`，显示“总数 / 本页范围 / 页码”。有数据但仅一页时仍显示结果范围；无数据时由空态承担反馈。筛选改变回到第一页，删除或结果收缩时把当前页限制在有效范围。

服务 PRD 原定每页 20 条；此次基于用户要求重新判断屏效，将高信息量服务卡片调整为 8 条。该调整属于本轮 UI 方案。当前演示仍为本地数组分页；接入接口时应将筛选、排序、页码和页长交给服务端，不把前端切片误认为数据懒加载。

若后续出现必须每页 50–100 行并连续批处理的明确需求，再单独采用列表容器内吸底的批量操作与分页栏；当前不增加这层固定区域。

## 5. 入驻、弹窗和订单详情

- **表单报错：** 字段红边及就地说明，带首个错误进入视野。提交总检查发现前面步骤未完成时，返回对应步骤直接标红。账户名称和法人姓名的一致性也提前在证件步骤检查。系统失败、文件异常和业务状态阻断仍使用系统反馈。
- **标题去重：** 入驻每步只保留页面标题与说明，演示填入移至标题右侧。表单分组采用竖线，删除编号装饰。
- **弹窗：** 按内容决定高度并在视口居中，最大高度为视口减 64px；超长正文独立滚动，头部和操作区可见。消除固定 margin 与居中 flex 布局冲突导致的拉高。
- **订单详情：** 标题 25px，区块标题 16px，表格正文 13px；组内保持紧凑，区块之间增加间距。五个进度节点用有边界的区块承载，完成项同时用勾选、绿色底板和状态文字表达。金额与阶段标题作为扫描锚点。
- **图片：** PRD 将展示尺寸留给 UI 确认；详情媒体本轮定为 4:3 展示框，使用 contain 完整保留原图比例。上传入口的 160×112 是控件规格，不能当作原图裁切要求。
- **商户档案：** 取消变更、继续编辑等头部操作在四个页签均保留，审核状态和权限仍沿用原逻辑。以本轮用户明确反馈覆盖此前仅基本信息页签显示的约定。

## 6. 实现与验证

共享入口：`src/styles/readability.css`；数字格式：`src/stores/commerce.ts`；历史金额文本：`MoneyText.vue`；分页：`ListPagination.vue`。页面局部变化保留在各自组件中。

已验证：

- 构建及类型检查通过；订单多阶段退款、支付、开票与商户变更既有检查脚本通过。
- 普通案例弹窗在 720px 高视口中高约 492px，上下留白约 114px，居中正常。
- 主体查询弹窗在 853px 高视口中高约 366px，底部无无效留白。
- 实际点击空表单下一步后，企业名称和识别码显示独立红边与错误说明，顶部无错误汇总。
- 入驻资质步骤只保留一个主标题，三组文档标题无编号且显示竖线；员工规模实际宽 320px。
- 1920px 宽屏下店铺资料、服务编辑器内容及编辑器头部实际宽度均为 1120px。
- 订单与退款金额实际渲染字重 700；旧历史的 `¥8,500.00` 已按 `¥8500.00` 显示。
- 商户管理切换经营资质页签后，头部编辑入口仍在。
- 三项技能已在独立演示表单中选中，渲染三个标签、折叠计数为 0；服务详情媒体实测 260×195px（4:3），图片使用 contain。
- 1200px 桌面下，订单详情主滚动区可用宽与滚动宽均为 1018px，没有横向溢出；服务筛选控件实测高 32px。

本轮只处理本地前端演示，未提交真实退款、付款、合同或开票动作。
