# 双端业务与项目把控

更新：2026-10-28。依据：用户对两个项目关系的说明、供应商端三份 PRD 与偏好卡、政企园区 README 和接口/设计资料。以下区分目标、现状和待定，不把原型当成已接通的生产能力。

## 产品关系

供应商端面向供给侧，承载供应商主体、入驻、园区关联、店铺、案例、服务发布与经营、订单履约及售后等。政企园区客户端面向园区企业用户，承载服务发现、了解商家与规格、发起服务需求及个人中心等。用户说明两个项目是一体的：供给侧创建的服务、关联园区以及交易数据需要支持园区侧使用。

**订单发起方、园区创建方和运营审核职责待逐流程核实。** 用户提到供应商端创建订单和园区；现有客户端资料也存在企业提交服务需求的路径。不要据此将申请等同订单或预设某一方独占创建权；先对照 PRD、页面及后端契约确定具体触发者与状态流转。

## 当前实现边界

- 供应商端为 Vue 3 / TypeScript / Vite 演示，业务数据与验收流程有本地模拟；不能宣称已接真实身份、审核、支付或跨端同步。
- 政企园区为 React / TypeScript / Vite，README 区分本地演示和 API 模式；服务申请成功不代表支付、合同成立或履约开始。旧交接和当前代码可能存在版本差异，开发前按实际路由和实现复核。
- 两端目前各有本地数据、模型和版本，不应假设共享数据库、浏览器存储或自动互通。跨端联调需先确认真实接口、环境、认证和数据归属。
- 金额、权限、审核、合同与交易最终状态应由可信服务端/相应平台确认；演示的计算与状态切换只用于演示，不能视为正式事实。

## 项目把控规则

1. 新需求先写清角色、对象、入口、前置条件、动作、结果及失败/恢复路径；标注来源与未决问题。
2. 跨端功能同时检查字段、命名、状态、可见性、时间与金额口径；区分当前数据和下单时快照。不要只修改一端的文案而让另一端语义失配。
3. 标记需求为已确认、现有演示、合理推断或待确认；冲突时记录冲突，涉及业务结果的决定不要自行定案。
4. 先复用各端现有页面模式和组件，新增能力在所属端落地；避免因统一而迁移技术栈或重写既有页面。
5. 验收分别记录构建/类型、实际页面交互、数据边界、跨端联调与业务负责人确认。演示通过不等于生产通过。
6. 不伪造认证、销量、审核、支付、承诺或客户数据；未接入的能力要有真实可理解的状态和后续路径。

## 联调前需要确认

统一服务和园区 ID；发布审核与可见性；价格、规格及订单快照；需求与订单转换；角色权限与 SSO；合同、文件存储；支付/退款/结算回调；发票和评价状态；接口版本、错误和幂等。以上是待对齐清单，并非已经定稿的接口设计。
